# ONNX Compatibility Fix Summary

## Root Cause

The `pass0_crash.onnx` file captured from the Android app crash is **not a standard ONNX ModelProto**. It contains a custom wrapper format that prevents the MNN converter from parsing it correctly.

## File Format Analysis

### Standard ONNX ModelProto Fields (from onnx.proto):
```
message ModelProto {
  int64 ir_version = 1;
  string producer_name = 2;
  string producer_version = 3;
  string domain = 4;
  int64 model_version = 5;
  string doc_string = 6;
  GraphProto graph = 7;                 // ← Standard field 7
  repeated OperatorSetIdProto opset_import = 8;  // ← Standard field 8
}
```

### Crash File Analysis (`pass0_crash.onnx`):
- **Field 1**: ir_version = 7 ✓
- **Field 2**: producer_name = "cam_isp_onnx_engine" (custom)
- **Field 7**: Nested message (119 bytes) with node names like "Slice", "CropBlock/starts" - this is a **custom wrapper**, not the GraphProto
- **Field 12**: START GROUP (deprecated protobuf syntax)

The file wraps the actual ONNX graph in a custom protobuf envelope at **Field 7** instead of writing the GraphProto directly at Field 7.

## Root Cause in cam-app

The `OnnxGraphComposer.kt` + `OnnxProto.kt` pipeline outputs standard ONNX correctly (using Field 7 for graph, Field 8 for opset_import). However, the crash file was generated by a **different code path** - likely `OnnxEngine.composeGraph()` in the cam-isp-onnx module which uses onnxruntime and may produce a different format, or some intermediate preprocessing step wraps the model.

## Fix Applied

**Reverted the incorrect change to `OnnxProto.kt`** - the original field numbers (7 for graph, 8 for opset_import) are CORRECT for standard ONNX.
